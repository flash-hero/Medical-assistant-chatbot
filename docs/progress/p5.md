### P5-D10: where the 503 time went (overload)
Every run had the single server process at 1.0 core, so a rejection's latency was queueing behind CPU work, not
waiting on I/O. Evidence (probe runs `overload-20261120T011915Z` / `-010629Z`, then in-process CPU
measurement `time.process_time` per request, then the gate run):
- the precheck, which every request must pass BEFORE admission (C9: emergencies bypass the queue), cost
  ~3 ms on mains power and 15-35 ms on battery (the same laptop at 2.3 GHz); cProfile: 80% in
  `lexicon_combos.find` (all groups of 155 combinations evaluated even when the first group had no span;
  ~1,000 memo lookups hashing a frozen dataclass each) and `_fuzzy_hits` (1,404 rapidfuzz
  `partial_ratio_alignment` calls, C code, ~12 ms on battery; a character-bound prefilter and `cdist` were
  both measured slower and dropped). Fix: early exit + identity memo; the scan output is identical on
  1,470 eval texts (120 with combination hits); precheck -40%.
- in a worker thread the precheck fought the event loop for the GIL: probe phases thread_dispatch p95
  112 ms + loop_resume p95 87 ms, against 0.03 ms with the precheck inline (diagnostic run), which shows
  the switch-interval convoy; with the cheaper precheck the thread is kept (no loop blocking for the
  streams) and the gate passes.
- streamed turns: `sanitize()` (per-character Python loop) ran on every released delta through the output
  checks: 45% of the event-loop thread's profile. Fix: regex fast path when no removable character is
  present (exhaustive test over all code points); served-turn CPU -12% on mains power.
- the earlier P5-D12 admission fix (a full queue refuses at once instead of after the 5 s wait).
A first re-run on battery power (`overload-20261120T142325Z`) refused 2 of 3,628 requests: the server
(53 ms CPU per request) could not take requests fast enough to fill the queue, so it did not measure the
rejection path. `evals/load/run.py` now writes no gate record when fewer than 25% of the chat requests
were refused (`OVERLOAD_MIN_REJECTED_SHARE`, test in `tests/chaos/test_chaos_load_harness.py`).
What remains is inherent to one worker: the precheck runs before admission by design, so at 3x
overload the rejection rate is bounded by one core's precheck throughput; production runs several workers.

### Soak: no leak; the 0.26 was session churn and stores still filling
- The 0.26 came from the steady run (50 users, a new session every 60 turns, 2 min warm-up). With churn,
  every new session stays in the memory session store for its 2 h lifetime (bounded at 50,000), and after
  2 min the bounded stores were still filling: replay frames reach their 2,000-entry cap after ~4 min,
  turn owners their 8,000 cap after ~11 min. Diagnostic re-run with churn and tracemalloc
  (`steady-20261120T153030Z`, 12 min, --no-write): RSS +27.8% while the traced Python heap shrank by
  22.7 MB between the warm-up mark and the end; the retained growth by line: replay frames
  (`core/schemas/events.py:146`) +1.34 MB (1,527 -> 2,000 = cap), turn owners (`app/api/gate.py:110`)
  +0.42 MB (1,527 -> 6,855, cap 8,000), the fake model's call log (`evals/fakes/fake_llm.py:82,116`)
  +1.09 MB, sessions 50 -> 149. Nothing in the app grows without bound.
- One harness leak fixed: the load server's FakeLLMProvider kept one tuple per model call (~100,000 per
  40-minute soak, ~2% of RSS); `load_llm()` now gives it a call log that keeps nothing (like the fake
  retriever's), test `test_load_llm_keeps_no_call_log`. The gate soak ran before this fix, so its value
  is conservative.
- The soak gate is a steady state: a fixed pool of 300 users, one session each for the whole run, 15-35 s
  think time (~28 streams in flight), production rate limits, RSS from the end of a 10 min warm-up
  (stores at their caps: sessions 300, replay 2,000) to the end. Stores over the window: sessions
  300 -> 300, replay 2,000 -> 2,000, turn owners 6,287 -> 8,000 (cap), rate-limit entries 1,244 -> 1,274.
  25,788 turns, 1 error (a client-side unparsed stream), server at 0.80 core.
